# 単語のスペル順・品詞フィルタと品詞マスタの表示順（Draft）

## 採用された要求と旧版との差異

現行要件正本 `100_機能仕様.md` の **LG-05・LG-07（2026-11-16利用者判断）** が規範である。

1. **単語一覧の順序**：スペル昇順のみ。品詞順や手動順への切替は不要。単語は1語につき1行のまま扱い、複数品詞を持っていても並べ替えの代表品詞を決めない。
2. **閲覧の絞り込み**：スペル・意味の検索と、品詞によるフィルタを提供する。品詞は単語一覧のソートキーではない。
3. **品詞マスタの順序**：品詞マスタは言語ごとに管理する独立した一覧。新規追加順を既定とし、作者が手動で並べ替えられる。運用上、言語の品詞が成立した順序を表現する。
4. **単語の品詞登録**：単語の意味に設定する品詞は、所属言語に既に存在する品詞マスタから選ぶ。マスタに未登録の任意品詞を単語の入力経路から作らない。1語が複数意味・複数品詞を持つことは許容する。

旧v0.3の「300_辞書共通機能.md」の「品詞、スペルでのソート順指定」は2026-11-16の解釈確認以前の表現であり、**単語一覧を品詞順で並べる要求として継承しない**。旧 `Language/Word/SelectPublicInfo` の `Spell` 昇順と、旧 `Language/Language/SelectPublicDetail` の `Dictionary_M_Class.Order` 昇順はそれぞれ**別の一覧**に適用される。旧版の文字列だけから、複数品詞の語をどの品詞でソートするかという規則を創作しない。

## 現行コードとの照合（観測、採用完了ではない）

`develop@0645d3aa8b1ab9aa0c14ea326df599a8f92f834e` の実コードで確認した不一致は次のとおり。

- `apps/web/app/pages/dictionaries/[id].vue` は単語に `order` → タイトル順を使用。新仕様の**スペル順固定**とは一致しない。品詞によるフィルタ・スペルと意味の検索自体は存在し、探索的Chromium/PGの限定証拠はPR #137にある。
- `apps/web/app/components/LanguageStructureEditor.vue` は品詞マスタの追加順を配列で保持しているが、**品詞項目の手動並べ替えUIがない**。
- `apps/web/app/components/WordMeaningsEditor.vue` はマスタが空の場合に自由入力を許し、既存のマスタ外値を「旧値」候補として保持する。新規単語作成の `apps/web/app/pages/studio.vue` もマスタが空の場合に自由入力する。新仕様のマスタ前提の通常入力経路と異なる。
- `packages/contracts/src/word-meanings.ts` は品詞を長さだけで検証する。所属言語の品詞マスタとの参照整合はこのバリデータ単体では実施されない。`language-structure.ts` のマスタ配列検査はID重複を拒むが、品詞名重複と参照中の名前変更・削除の扱いは別途精査する。

## 既存データ・参照操作の設計境界

以下は**ユーザー未確認の設計条件**であり、今回の決定から一意には導出できない。実装時に現在の実データ・旧仕様・公開版/下書き分離を調査し、必要な判断だけを規範化する。

- **既存のマスタ外品詞値**：現行コードには自由入力経路が存在する。読み込み時に削除、暗黙にマスタへ追加、他品詞へ強制変換することはしない。既存値の移行・表示・保存拒否範囲を検討し、新規にマスタ外値を作れる通常経路は閉じる。
- **品詞マスタの改名・削除**：既存の単語意味が品詞名で参照しているため、参照中のマスタ項目の改名/削除時に拒否・伝播・論理移行のどの設計を採るかは要検討。特に下書き変更だけで読者の公開版を書き換える設計は採用済み公開分離に反する。
- **整列比較の細部**：ユーザーが承認したのは「スペル昇順」。Unicode正規化、創作言語固有の照合規則、大小文字の扱い、異言語をまたぐ単一一覧の合成順は別設計であり、無断で追加要件としない。現在の `localeCompare(..., 'ja')` は既存実装上の照合方式として検証対象となる。

| ID | 操作 | 期待 |
| --- | --- | --- |
| DICT-01 | ある言語で登録/手動順とスペルが逆転した公開語を複数配置 | 言語内の単語一覧はスペル昇順になる。品詞マスタの並べ替えに左右されない |
